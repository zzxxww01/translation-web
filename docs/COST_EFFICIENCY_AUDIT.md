| 相同物理模型、provider 和 key 的多个别名重复占 fallback 槽位 | 按实际路由去重，仍保留最多四次尝试与官方兜底；只有单一路由时允许一次暂态重试。 |

| Gemini 超时线程丢 ContextVar | 提交时复制上下文，保留截止时间、限流、取消和输出上限。REST 同样受外层总预算约束。 |

| 累计请求时长被误当墙钟耗时 | 保留 duration_seconds 兼容字段并显式标为累计 service_seconds，另提供 wall_elapsed_seconds。并发调用服务时间可以大于任务实际等待时间。 |
| 固定提示词前面插入动态章节内容 | 审校/修订的共享规则保持稳定前缀，上下文作为模板中的明确数据段落；移除修订中重复的同一问题描述。没有删除原文、逻辑约束和完整复核。 |
| 没有术语候选仍调用验证模型 | 空候选直接跳过该次调用，不跳过文章分析或任何已有候选的验证。 |

## 2. 先看成本结构，不先换“最便宜”的模型

一次章节处理的正常调用数近似为：

`章节调用数 = 初译批次数 + 1 次审校 + 定点修订批次数 +（内容实际变化 ? 1 次完整复核 : 0）`

目前初译最多每批八段（同时受源文字符预算约束），定点修订每批四个问题段落。文章级还要加深度分析、非空术语验证、章节角色分析、标题/来源元信息、预扫描，以及实际启用的质量报告/规则学习等。一次 generate 内还有有界传输重试，不能把“四步法”当作固定四次 API。

例如一个章节有 20 段、6 个需要修订的段落，假定字符上限不先触发，则正常链路为 `3 + 1 + 2 + 1 = 7` 次生成。这里是代码路径推导，不是生产请求统计；文章级前置工作和网络重试另算。

总成本应以“验收通过的段落/文章”为分母：

`预期模型成本 = 初译成本 + 审校成本 + 进入修订概率 ×（修订成本 + 复核成本） + 失败/重试成本`

强初译模型值得采用的条件之一为：

`强模型初译溢价 < 修订率下降 ×（修订成本 + 复核成本）`

还应加入人工修改耗时；低单次价格但错译、重译更多的组合可能更贵。不能只比较每百万 token 单价，也不应只优化“调用数”：把大量内容塞进一次调用可能增加截断、错位和整批返工。

## 3. 成本账本与估算工具

新增离线命令：

```sh
python -m src.cli.cost_report path/to/run-summary.json --rates path/to/your-actual-prices.json
```

输入可以是 llm_usage 对象，或带 llm_usage 的运行工件。`config/llm_prices.example.json` 默认 rates 为空，不伪造报价；请按实际 provider_id + real model 精确填写所选计价期、币种、价格来源与三类单价。币种分别汇总，未定价组为 missing_price，不按 0 元显示。上游官方 API 价格不能替代 VectorEngine 等中转商的真实扣费规则。

本工具只估算已观测完成调用的平价输入/缓存读取/输出 token。部分缓存用量未知时给所选平价范围；输入/计费输出未知则保留 unpriced。报告始终 `invoice_complete=false`：缓存写入溢价、存储、工具、阶梯价格、税费、中转加价、失败时未返回 usage 和关闭任务之后的迟到 usage 都需要额外对账。旧工件没有新的分组/计费字段时不臆造完整账单。

一般账务模型需要：

`C = Σ[(普通输入 × 单价) + (缓存读 × 单价) + (缓存写 × 单价) + (计费输出 × 单价)]/10^6 + 缓存存储 + 工具 + 中转附加费 + 税费`

各字段是否相互包含必须按实际供应商协议核对，避免重复加 reasoning、把缓存写费漏掉，或用展示字符数估算精确 token。输出上限不代表预先支付整个上限，但过小会提高截断/重试风险。

## 4. 推荐的优化顺序

### 直接启用本次修复

先去掉无效请求、重复路由、超预算重试、无候选术语验证和重复提示文字，纠正用量统计与未生效的配置。这些是可定位的实现缺陷，不需要牺牲检查范围。注意原先被忽略的 8192 等 max_tokens 配置现在真正生效，部署时要观察截断率；复杂推理模型的 thinking 与正文可能共享输出预算。

### 缓存：先可观测，再按通道适配

固定规则前置只是必要的准备，不保证缓存命中。检查实际缓存 token 比例、首次请求写入费用、存储 TTL 和相同前缀的复用次数；不要为了达到最低缓存长度补无用文本。不同模型/API 可能需要显式断点；兼容 OpenAI 的中转协议不代表支持 OpenAI 全部缓存语义。

把三种缓存分开：供应商前缀缓存复用计算，仍会生成新答案；本地结果缓存直接复用答案；分析工件缓存复用既有已验证步骤。本地缓存至少按原文、相关上下文、提示词/术语/规则版本、模型和参数、编辑意图及权限作用域建立键。用户要求重译时默认不回放旧答案；人工编辑、失败、残缺结果和跨项目相同文本都不能盲目复用。后两类缓存没有在本次贸然全局启用。

### 模型与推理档位：按任务评测

文章论证、歧义与保真审校保留较强模型。标签、已消歧术语格式化、已明确的标题格式整理可作为较小模型/低推理候选。精修失败、事实复杂或结构冲突时再升级。先用保留语料比较整条链的验收成本，不因为任务名称“标题”就无条件换便宜模型。

建议提供 quality / balanced / economy 三种显式策略供用户选择；默认仍保持当前质量边界。economy 不应默默跳过保真审校，降低的是非必要解释输出、可复用辅助工作与适当任务的模型档位。改变正文输出或审校覆盖需要明确产品决定与质量证据。

### 复核：保留当前完整检查，测量增量方案

当前修改后完整复核是可靠但有成本的保障。候选方案是“修改段落 + 必要邻段/指代 + 涉及术语的影响范围”增量复核，未变部分按哈希复用旧检查。修改跨段指代、条件、标题、术语或论证结构时升级到整章。没有证明覆盖可靠前不要仅改 review(v1) 标签当作 v2 审校，也不要直接关闭复核。本次未默认降低审查范围。

### 并发：按约束调优，不盲目拉满

吞吐受有效并发/平均请求时间、RPM、TPM、模型输出速率、连接池及写盘共同限制。上游限流后继续加线程会增加失败与等待。记录请求入队、开始传输、首 token/完成、重试和最终验收时间，再按任务和通道看 P50/P95。当前新限流器共享一个进程内 provider 配额；多个进程需要统一配额。正在执行的阻塞 HTTP 无法通过取消 future 瞬间收回。

建议让交互式单段修改优先于整篇后台任务；批量任务使用有界队列和背压。没有生产负载数据，不在此硬给“最佳并发数”。初译按字符打包是防极端大批次的启发式，后续可按各模型 tokenizer 与保真结构进一步估计输出预算。

### 真正的 Batch API：只用于不着急的工作

本仓库将若干段落放进同一个 prompt，不等于供应商 Batch API，也不会自动享受 Batch 价格。Google 文档规定 Gemini Batch 为异步处理，标准价的 50%，目标周转 24 小时。它适合评测集、夜间整批导入等；不适合当前需要立即响应的段落编辑。依赖上一阶段输出的多阶段翻译还需要分批编排，不可当成一次无状态批处理。中转商是否支持与如何计费另行确认。

## 5. 已测量与尚未测量

本轮本机微基准：一个 provider/model/phase、5000 条已完成调用，紧凑汇总轮询 100 次一组，共 7 组。基线每次中位 **1.2134 ms**；修改后 **0.0109 ms**。这是状态汇总函数的微基准，不是吞吐、真实翻译时延或费用节省比例。代码复杂度从逐调用扫描变为读取预聚合值（另遍历分组）；多 provider/phase 下开销随组数增长。超过明细上限后 token/调用计数仍完整。

离线测试验证总 deadline、取消后不继续发送、provider 配额、SDK 上限与 thinking 用量、截断结果的已知费用、同物理路由去重、超过明细容量的总量、价格缺失和币种隔离、批次 ID、稳定前缀和问题描述去重。真实模型测试默认关闭，最终完整 CI 数量及 Chromium 构建结果见 PR；不要用该文档提前宣称尚未完成的运行成功。

下一步验收建议使用一组开发样本及独立保留样本，覆盖长技术文章、长定语、让步/条件、数字单位、跨段指代、词义与多轮编辑。按相同模型和输入做旧/新对照，再逐项改变模型、推理档位和缓存。统计总输入/缓存读写/正文与思考输出、失败/重试开销、端到端 P50/P95、严重错误率、无需人工修改率、人工分钟数与每千字验收成本；报告样本数、每次输出和变化原因。没有生产用量与实际价目表，本次不报告虚构的每篇价格或节省百分比。
